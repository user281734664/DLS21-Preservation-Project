# Research Environment and Requirements

This page explains **what is required for each part of the DLS21 Preservation Project**, what is already contained inside the original APK, what must be supplied separately, and which tools are only needed for advanced research.

The project has several different workflows. A researcher who only wants to reproduce the LAB APK does **not** need the same tools or files as someone continuing the Ghidra reverse-engineering work.

---

## Target build

The primary preservation target is:

```text
Game:        Dream League Soccer 2021
Version:     8.13
versionCode: 38
Package:     com.firsttouchgames.dls7
Native lib:  libDLS21.so
```

The repository does **not** distribute the original APK or proprietary game assets. Researchers must provide their own compatible copy of DLS21 v8.13.

# Choose your goal

## A. I only want to reproduce the LAB / USER-CA APK

You need:

- your own original DLS21 v8.13 APK;
- Python 3.10 or newer;
- Java / JDK;
- Apktool;
- Android SDK Build-Tools:
  - `zipalign`
  - `apksigner`

Run:

```bash
python tools/make_lab.py DLS21_813_original.apk
```

On Windows:

```bat
tools\make_lab_windows.bat "C:\path\to\DLS21_813_original.apk"
```

Expected output:

```text
DLS21_813_USERCA_LAB_signed.apk
```

### Do I need libDLS21.so separately?

**No.** Not for this workflow.

`libDLS21.so` is already contained inside the original DLS21 APK. The builder carries the native library through the APK rebuild and checks its SHA-256 before and after the process.

The patcher intentionally does **not** modify:

- `libDLS21.so`;
- `classes*.dex`;
- game assets;
- `players.dat`;
- `teams.dat`;
- `teamplayerlinks.dat`;
- Frontline protocol logic;
- gameplay logic.

The deliberate LAB changes are limited to the Android application configuration needed for research:

- `android:debuggable="true"`;
- USER-installed CA trust for `api.ftpub.net`;
- APK rebuild / zipalign;
- local research signature.

See [APK_PATCHING.md](APK_PATCHING.md).

## B. I want to install and test the LAB APK on Android

In addition to the requirements above, you should have:

- an Android test device;
- ADB / Android Platform Tools;
- USB debugging enabled, or another working ADB connection.

The LAB APK is signed with a **local research key**, not the original First Touch Games publisher key. Because the signatures differ, the LAB build normally cannot be installed directly over an official installation.

Typical clean installation:

```bash
adb uninstall com.firsttouchgames.dls7
adb install DLS21_813_USERCA_LAB_signed.apk
```

Useful check:

```bash
adb shell run-as com.firsttouchgames.dls7 id
```

If the LAB patch is active and Android accepts the application as debuggable, `run-as` should succeed.

### Current validation status

A previously created USER-CA LAB build was used successfully during the project research.

The repository's final `tools/make_lab.py` reproduces that patching approach and performs structural/hash checks. However, a **fresh APK generated by the final public script has not yet been physically installed and validated on a clean Android device**.

That is a useful first verification task for a future researcher.

## C. I want to run the local DLS21 mock / offline research environment

You need:

- the LAB / USER-CA APK;
- Python 3;
- mitmproxy / mitmdump;
- `mock/dls_mock.py`;
- the mitmproxy CA installed on the Android device as a **user certificate**;
- the phone and research PC on a network path where the phone can reach the proxy;
- the Android Wi-Fi proxy pointed to the research PC.

Typical Android proxy configuration:

```text
Proxy: Manual
Host: <PC LAN IP>
Port: 8080
```

Typical mock launch:

```bat
mitmdump -s mock\dls_mock.py ^
  --listen-host 0.0.0.0 ^
  --listen-port 8080 ^
  --set connection_strategy=lazy
```

Historical Frontline host used by the project:

```text
api.ftpub.net
```

# Database files

The core DLS21 database trio is:

```text
players.dat
teams.dat
teamplayerlinks.dat
```

The mock uses:

```text
DBp -> players.dat
DBt -> teams.dat
DBl -> teamplayerlinks.dat
DBv -> common database version
```

## Are these files required?

### For building the LAB APK

**No.**

The APK builder does not require the three DAT files.

### For basic mock testing

**Not necessarily.**

The current mock can generate a small fallback LAB database when no valid external database trio is available. That fallback exists only to test engine/protocol paths.

It is **not an original DLS21 database**.

### For a faithful DLS21 reconstruction

**Yes.**

A complete preservation effort ultimately needs valid:

- `players.dat`;
- `teams.dat`;
- `teamplayerlinks.dat`.

The original complete server database trio has **not** been recovered by this project.

Tiny bootstrap/test files encountered during research must not be confused with complete original databases.

See:

- [PLAYERS_DAT_FORMAT.md](PLAYERS_DAT_FORMAT.md)
- [../STATUS.md](../STATUS.md)

# libDLS21.so

This file has two different roles in the project.

## When building or running the LAB APK

You do **not** need to find or download `libDLS21.so` separately.

It is already contained in the original APK, normally at:

```text
lib/armeabi-v7a/libDLS21.so
```

The LAB builder preserves it and checks that its bytes did not change.

## When continuing native reverse engineering

A standalone extracted copy of `libDLS21.so` is effectively required.

This is the native DLS21 engine binary analyzed in Ghidra. It contains the code paths from which the project identified, among other things:

- player runtime structures;
- overall/rating calculation;
- card rarity/tier calculation;
- the auxiliary `0x46` player record;
- database-related strings and code;
- Frontline-related strings and behavior.

A researcher can extract it from their own original APK. An APK is a ZIP-compatible container, so it can be inspected with common archive tools.

Do not treat a `libDLS21.so` taken from an unrelated DLS19/DLS20 conversion as equivalent to the original DLS21 engine.

# Ghidra / native reverse engineering

Ghidra is **not required** to run the LAB APK or the mock.

It is needed if the researcher wants to continue native reverse-engineering work.

Useful currently documented functions:

```text
FUN_0035d84c  player runtime construction/update
FUN_0035fd94  overall/high-precision rating
FUN_0035fe88  card tier classifier
FUN_00471694  find/copy 0x46 auxiliary record
FUN_00471604  copy auxiliary-record array
FUN_00472290  development/progress calculation
FUN_00472384  access another field in the same record family
FUN_00475bd0  large player/config global copy
```

Main open native-research target:

```text
auxiliary player record +0x04
```

Known beginning:

```text
+0x00  uint16  Player ID                       [PROVEN]
+0x02  uint16  baseline high-precision rating  [PROVEN]
+0x04  uint16  UNKNOWN                         [OPEN]
```

Current rarity path:

```text
rarity_score =
    uint16(aux + 0x02)
  + uint16(aux + 0x04)
```

Do not name `+0x04` as "potential", "rarity bonus", "development", or another semantic field until the native data flow proves it.

# Recommended path for a new researcher

## Reproduce the environment

```text
1. Obtain your own original DLS21 v8.13 APK
2. Install Python + JDK + Apktool + Android Build-Tools
3. Run tools/make_lab.py
4. Install the generated LAB APK on a test Android device
5. Confirm run-as works
6. Install your own mitmproxy user CA
7. Configure the Android Wi-Fi proxy
8. Run mock/dls_mock.py
9. Verify requests reach mitmdump
```

## Continue preservation research

After the environment works:

```text
10. Extract libDLS21.so from your own original APK
11. Open it in Ghidra
12. Read CONTINUE_HERE.md
13. Continue tracing auxiliary record +0x04
14. Work toward valid complete players.dat / teams.dat / teamplayerlinks.dat
15. Keep PROVEN / IN PROGRESS / HYPOTHESIS labels separate
```
